# 技术设计总览：缓存足迹优化

> 本文件只写**四项改动共享的架构决策**与它们之间的相互作用。每个子任务的具体设计在其 `design.md`。

## 问题的三层结构

实测把「占内存」拆成了三个互不相同、互不替代的问题：

| 层 | 现象 | 实测 | 对应需求 |
|---|---|---|---|
| **存储层** | 单条描述未截断 | 817 条候选中 74 条（9%）>512 字，贡献 97% 体积；单条最长 241,896 字符 | R1 |
| **进程层** | 内存 Map 无上限、无淘汰 | 11 条大条目全驻留约 13 MB；理论无上限 | R2 |
| **磁盘层** | 过期文件永不删除 | 41 文件 / 11.22 MB，其中 26 个已过期 / 6.61 MB（59%）是垃圾 | R3 |
| （分发层） | 开发物进包 | 91 文件 / 2.07 MB，开发物占 60% | R4 |

**关键洞察：三层必须一起修，任何一层单独修都会被另外两层吃掉。**

- 只修 R1（截断）：磁盘降到约 0.5 MB，但进程仍可能持有 64 条 × 旧格式的大条目，且旧垃圾文件仍在盘上。
- 只修 R2（内存上限）：磁盘 11 MB 不变，重启后仍从盘上读回大条目。
- 只修 R3（磁盘 GC）：删了垃圾，但新写入的仍是 1.43 MB 的全量描述，几小时后垃圾重新长回来。

## 层间相互作用（这是设计里最容易漏的部分）

### R1 → R2：上限的「条数」口径依赖 R1

R2 用 64 **条**而非字节数做上限，因为按字节需要在热路径上重新序列化。但这个选择的合理性**完全建立在 R1 之上**：

- R1 之前：单条可达 1.43 MB，64 条 = 最坏 91 MB —— 上限形同虚设。
- R1 之后：单条约 16 KB，64 条 ≈ 1 MB —— 上限才真正约束住内存。

**这就是 R2 必须排在 R1 之后的原因，不是排期偏好。** 若顺序颠倒，AC2.5 的「heap 增量 <20 MB」几乎必然失败。

### R1 → R3：64 MB 阈值在 R1 之后几乎永不触发

R1 把稳态从 11 MB 压到约 0.5 MB 后，R3 的总量上限（64 MB）实际上不会触发。**这不是 bug，但必须验证它不是「因为失效才不触发」**——所以子任务 AC3.2 要求用 5 个 20 MB 的造数据文件单独证明上限仍有效。

若不做这条验证，将来有人看到「上限从没触发过」会误以为代码死掉。

### R2 与 R3 同文件、不同区域

两者都改 `src/cache.ts`：

- R2 改 `memory` 相关（`:102`、`:186-210`、`:224-241`）；
- R3 改磁盘清扫（新增函数 + `cacheSet` 的 `rename` 之后一行）。

区域不重叠，但串行提交避免并发编辑冲突；`git revert` 任一都不会破坏另一个。

### R4 依赖前三者的最终产物

R4 打包的是最终 `lib/`，必须等 R1–R3 的源码全部稳定。否则要重新打包、重新核对体积。

## 贯穿四项的不变量

这些在任何子任务中都**不得**改变（父任务 AC7 逐条核对）：

| 不变量 | 值 | 为什么不能动 |
|---|---|---|
| 渲染预算 | `MAX_DESCRIPTION_CHARS = 200` | 卡片宽度与 `render-table.test.mjs` 依赖 |
| 引用长度 | `SUSPICION_QUOTE_CHARS = 120` | 证据链格式 |
| 判重阈值 | `SCORE_GAP_SIMILARITY = 0.6` | 排序稳定性 |
| 内存 TTL | 5 分钟 | 决定「重复调用是否联网」 |
| 磁盘 TTL | 24 小时 | 决定配额节省 |
| 源码 TTL | 10 分钟 | `inspect_projects` 的可信度契约 |
| 依赖 | `dependencies: {}` | 零运行时依赖是项目立场 |
| 缓存位置 | `$DSH_HOME/cache/dsh-find-ideas` | 用户可预期 |

## 缓存版本号的语义

`CACHE_VERSION`（`src/cache.ts:23`）是**运行时开关**，不是元数据。R1 必须 2→3，因为 `data.description` 的长度语义变了：

- 不升版本 → 旧条目（全量）与新条目（512 截断）混在一起，同一 idea 的描述长度在两者间随机跳，且**不报错**。
- 升版本 → 旧条目全部 miss，代价是每个不同 idea 一次 re-fetch。

`src/cache.ts:12-22` 的 1→2 注释已经把这个权衡写透了：「Ignoring the old entries costs one re-fetch per distinct idea; reading them costs a wrong answer that looks right.」R1 照同样写法补 2→3。

**这是唯一一个「看起来是元数据、实际是行为开关」的常量**，也是回滚时的安全阀：旧代码读到新格式会当作 miss，绝不会读出错值。

## 失败模式与降级

四项改动全部遵循既有的 best-effort 契约（`src/cache.ts:238-240`）：

| 失败 | 行为 |
|---|---|
| 磁盘不可写 | `cacheSet` 静默失败，`cacheGet` 走网络 |
| 磁盘条目损坏 | JSON 解析失败 → 当作 miss |
| 清扫抛异常 | 吞掉，`cacheSet` 不受影响 |
| 内存被淘汰 | 回退到磁盘；磁盘没有就 miss |
| 版本不匹配 | 当作 miss |

**没有任何一条会让工具报错**。这是刻意的：缓存是加速器，不是数据源，它的任何故障都不该让 `scout_projects` 失败。

## 被明确拒绝的整体方案

| 方案 | 拒绝理由 |
|---|---|
| 换用 SQLite 存缓存 | 新增原生依赖，违反 `dependencies: {}`；且问题不是查询能力而是数据本身太大 |
| 缓存整体 gzip | 磁盘降了但内存仍是全量；每次读要解压，热路径变慢 |
| 只存渲染后的字符串 | 会丢掉 `similarity()` 与证据链需要的原始字段，改变排序行为 |
| 把缓存移到 OS temp 目录 | 破坏用户可预期性，且清理时机不可控 |
| 加 `dispose` 钩子做定时清理 | 插件生命周期钩子不稳定；`setInterval` 会阻碍进程退出 |

## 验收的分层

- **单任务层**：每个子任务自己的 AC（可执行、附证据命令）。
- **集成层**：`implement.md` 的 I1–I5，含**叠加效果**验证（I2）——这是最容易漏的一层，单看每项都合格不代表叠加后合格。
- **不变量层**：AC7 逐条核对未改动项。

三层都过才算完成。
