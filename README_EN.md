## Demo

Describe your idea in one sentence. The agent searches GitHub for similar projects, ranks them by relevance weighted with stars, and returns a card. Pick a few repositories from it and the agent reads their README, dependency manifest, directory tree and key files, then writes up a technical proposal you can borrow from.

![a ranked card and the repository inspection that follows it](https://github.com/user-attachments/assets/e17fcf47-6aa1-45ef-830f-dc3885121908)

## Install

```sh
# from npm (recommended)
dsh plugin --profile web add dsh-find-ideas

# or from GitHub
dsh plugin --profile web add github:tianyao2003/dsh-find-ideas
```

### Configure a GitHub token (recommended)

GitHub limits unauthenticated search requests to **10 per minute per public IP**, and everyone behind the same egress IP shares that quota. A token raises it to **30 per minute**, counted per account.

The plugin reads `GITHUB_TOKEN` through DSH's credential store. Set it in the environment that launches DSH:

```sh
export GITHUB_TOKEN=ghp_...          # bash
$env:GITHUB_TOKEN = 'ghp_...'        # PowerShell, current session
```

Everything works without a token, but `inspect_projects` refuses an anonymous batch it estimates above 10 requests.

## Usage

Restart dsh after installing, then describe your idea — the agent calls the four built-in tools on its own:

- "I want to build a local-first Markdown note app — what's out there on GitHub?"
- "I want to build a UI-enhancing DSH plugin. Which projects exist?"

## The four tools

![architecture](docs/dsh-find-ideas-architecture.png)

| Tool | What it does | Limits |
| --- | --- | --- |
| **`scout_projects`** | Turns the idea into several GitHub search queries and returns a star-sorted pool — deliberately *not* ranked by relevance | Translates an idea with no Latin letters into English search terms first; when that is impossible it returns `plan_failed` |
| **`rank_candidates`** | Scores the pool with the formula and produces the card | Accepts either a single 0–10 `relevance` or the `problem_fit` / `workflow_fit` / `technical_fit` dimensions (0–5) it derives from |
| **`inspect_projects`** | Reads a repository's README, dependency manifest, tree summary and key files | Up to 5 repositories per call; about 6 requests per repo at `shallow`, about 10 at `deep`; the card is capped at 24 KB |
| **`read_repo_files`** | Point-reads files of one repository at a **single commit**, returning a line window and a permalink with the commit and line range | Up to 4 files per call; `max_bytes` defaults to 8000 (4000–8192) and is a ceiling, not a suggestion |

`read_repo_files(view="architecture")` adds a bounded architecture reconnaissance pass: entry points, direct dependencies, route or command registrations, data model declarations, conservative two-hop call chains, external service boundaries and observed test behaviour. Every item carries a path and line anchor when available; unsupported or unread areas are reported as unknown, and no complete call graph is claimed.

## The card

- Eight columns, always in that order: rank, project link, last updated, relevance, stars, score, language, one-line description.
- The ranking formula is `relevance × (1 + log10(max(stars, 10) + 1)) / 2`, computed in code and not settable from prose.
- `relevance` is the caller's judgement; the tool neither computes it nor checks whether it is right. With dimensions, the card adds a separate section listing each dimension, `borrowability` and a confidence level, where `?` means unmeasured.
- A number nobody measured is never written as `0`: a query term never tested on its own reads `未知（未测得）` ("unknown — not measured"), a missing archive count reads `数据缺失` ("data missing"). The card itself is written in Chinese, so those are the literal strings it emits.
- Repository text is quoted as data, so a line of README cannot impersonate card structure; links are only ever `github.com` or `raw.githubusercontent.com`.
- Nothing throws: a failure comes back as a `reason` and a `detail`, and a partial result says why it is partial.

## Caching and what leaves your machine

- In memory: up to 64 results, 5 minutes.
- On disk: search results 24 hours, source reads 10 minutes, capped at 64 MB and swept about once an hour.
- A bounded local prior file records repository names, timestamps, counts, commit/path metadata and hashed idea identifiers. It never stores source or raw idea text, is capped at 256 records / 64 KB, and is shown as context only; it does not change ranking.
- All of it under `$DSH_HOME/cache/dsh-find-ideas/`, and deleting that directory is always safe.
- Search queries and repository paths go to `api.github.com`; `inspect_projects` and `read_repo_files` only read repository content on GitHub, so your local code is never uploaded. The one other destination is the model DSH already uses, and only to translate an idea with no Latin letters when the caller supplied no Latin `keywords`; a purely English idea is never sent anywhere for translation.

## Known limits

- **The ranking is a heuristic, not a recommender.** The formula treats star count as a weight, so popular projects win by default; a closer but obscure match has to be picked out of the pool by hand.
- **Search covers names, descriptions and topics only.** GitHub search does not index README bodies or file contents, so a project described only in its README is missed — `inspect_projects` is what closes that gap.
- **A Chinese idea with no English search terms reaches nothing.** Projects that describe themselves in English are close to unreachable through a Chinese query, so the tool refuses and explains why instead of returning unrelated results.
- **`inspect_projects` samples, it does not read everything.** At most 4 files per repository at `shallow` and 8 at `deep`; the architecture view never claims a complete call graph.
- **The card is capped at 24 KB.** When it does not fit, evidence is trimmed cheapest-first (manifest, then README, then per-file excerpts, then the signature skeleton) with a note saying what was withheld and how to get it back — point-read it with `read_repo_files`, or send fewer repositories next time.

A tool that does not tell you where its limits are is not worth installing.

## Compatibility

Requires Node ≥ 22. The `@deepseek-ai/dsh-tools` peer range accepts every published version from `0.1.0-rc.6` on, which covers the current DSH release lines — `latest` (0.2.1-rc.2) and `next` (0.2.1-rc.3). 

## Version

| Version | What changed |
| --- | --- |
| 0.4.1 (current) | Explainable relevance dimensions (`problem_fit` / `workflow_fit` / `technical_fit`, 0–5, deriving a 0–10 relevance with fixed weights, while the legacy single relevance input stays accepted); an evidence-anchored `view="architecture"` for `read_repo_files`; and a bounded local prior (256 records / 64 KB) that stores metadata only, is shown as context and never changes ranking. |
| 0.4.0 | Added `read_repo_files`; `inspect_projects` cards are capped at a fixed 24 KB and state the recovery paths when they overflow; the four tools' schemas are 1.7 KB smaller, repositories are read three at a time, and the card states its framing once instead of per file. | 0.3.0 | Cache and package footprint. Descriptions are stored at 512 characters instead of unbounded, the in-memory cache is capped at 64 entries, the disk cache sweeps expired entries and stays under 64 MB, and the published package no longer ships `src/`, `test/`, `scripts/` or source maps — 805 KB unpacked instead of 2.07 MB. Tool names, parameters and output are unchanged. |
| 0.2.1 | Published to npm. Same functionality as 0.2.0. |
| 0.2.0 | The card shows how many query channels found each row and how many rows are archived repositories. |
| 0.1.0 | First usable version: the `scout_projects` → `rank_candidates` → `inspect_projects` chain. |

## Contributing

Issues and pull requests are both welcome.

- **Report a problem or ask for a feature**: open an issue with the idea you typed, the result you expected and the result you got.
- **Change the code**: fork, branch off `master`, make the change with a test, run `npm run check && npm test` until green, then open a pull request. CI runs the same two commands on Node 22 and 24.
- **One change per PR**: a PR solves one problem; commit messages use prefixes such as `feat:` / `fix:` / `docs:` / `chore:`.
