# 检索金集与人工标注

这份文档解决一个具体问题：插件的 6463 条断言只证明了「跑得通、输出诚实」，**没有证明「找得对」**。金集是唯一能把「找得对」变成数字的东西。

配套文件：

| 文件 | 作用 |
|---|---|
| `labels.yaml` | 唯一真源：12 个 idea 的注册表 + 每条 (idea, repo) 的标注 |
| `pools/<ID>.yaml` | 每个 idea 的盲构造候选池（20 条左右，不含 star） |
| `README.md` | 本文档：规则、流程、判定标准 |

> **分发警告**：本文档含 `seeds` 与 `expected`，等于答案。给第二标注者只能发第 8 节，不要发整份文件。

---

## 0. 这份金集回答什么

端到端命中是一个乘法，不是一个数：

```
P(期望仓库进最终榜) = P(进候选池) × P(进榜 | 进池)
                       召回            判分
```

两者修法完全不同：前者改查询计划 / 翻译 / 长尾通道，后者改 relevance 引导或打分公式。合并成一个「准确率」就永久失去归因能力，所以金集必须分开记。

**三个指标：**

| 指标 | 定义 | 读法 |
|---|---|---|
| `Recall@pool` | 期望仓库进候选池的比例 | 检索层 |
| `Recall@board` | 进池的期望仓库里，进最终榜（top 10）的比例 | 判分层 |
| 长尾入榜率 | `<500★` 的期望仓库进 top 10 的比例 | 公式的 star 项是否过强 |

外加一个**不算插件错**的口径：`reachable: false`（检索面天花板）。期望仓库的 name / description / topics 里一个 idea 词都没有时，GitHub 的默认检索面就看不见它——这是平台约束，不是插件缺陷，必须从分母里剔出去单列。不剔的话，所有检索类工具都会被这个指标冤枉。

**必须先算随机基线。** 池子里每条都是从近似查询里捞出来的，所以期望仓库占比天生很高（本次 12 个 idea 的 gold set 占池子 20%–75%）。随机抽 10 条就期望命中 `gold 数 ÷ 2` 个——`Recall@pool` 必须和这个基线一起报，否则「召回 60%」可能还不如瞎抽。E1 的每条记录至少带四个数：**命中数 / gold 总数 / 随机基线 / 命中数 − 基线**。

**这份金集不回答：**

- 「有没有我没想到但更好的仓库」——标注只能锁住已知答案，这个缺口由 E3 的人工抽检补
- 统计显著性——12 ideas × 3 仓库 = 36 对，10 个百分点的差异在噪声内。**结论只做方向判断，报告里不许写「提升 X%」**

## 2. 标注 SOP

| 步骤 | 干什么 | 工时 |
|---|---|---|
| 0 | idea 已定稿（本仓库已完成），补 3–5 个 `reachability_keywords` | 0（已做） |
| 1 | 每个 idea 盲构造 20 个候选 + 2 个干扰项 | 0（已由脚本完成，见下）|
| 2 | 用 `labeling.html` 自标 240 条 | 60–80 min |
| 3 | 第二标注者盲标同一批（同一个 html，切到 B）| 外包，同量 |
| 4 | 导出 JSON + `merge-labels.mjs` 算 κ、定 expected set | 10 min |
| 5 | 脚本补 `reachable` / `reachable_evidence` / `star_band` / `archived` | 0（第 4 步一起做）|

### Step 1 盲构造候选池

v2 起已有现成的池子：`.scratch/build-pools.mjs` 直连 GitHub REST 建好，写进 `pools/<ID>.yaml`，并已注入 `labeling.html`。
每个 idea 四条通道：`search`（≤7 条，产品级关键词搜索）· `readme`（≤7 条，同义改写 + `in:readme` 宽搜）· `memory`（`labels.yaml` 里登记的种子）· `interference`（2 条故意错域的查询结果）。细则见 `pools/README.md`。

你要做的是**核对**，不是重建：12 个文件是否都 20 条 · 有没有明显该出现的仓库不在里面（记进 `notes`，不要偷偷加）· 2 个干扰项是不是真的错域（看 `interference` 字段，只在实验者视角可见）。

**硬规则：先建池，后跑插件。** 池子一旦被插件输出污染，这个 idea 整个作废重来——污染是不可逆的，你看过就再也回不到盲态。

### Step 2 自标

双击 `eval/labeling.html`（纯本地、不联网，标注存 localStorage）。一次显示一个 idea 的 20 条，`J/K` 移动、`1/2/3` 标 `Y/N/U` 并自动下移，标完点顶部「导出 JSON」。

- 理由按档位自动填默认值，可下拉改成更准的；导出时会标出还用着默认理由的条目
- 关掉浏览器不会丢；换人用顶部下拉切 A/B，两人数据分开存
- v2 把「轮转标注」改成「按 idea 批量标」：同一 idea 的 20 条横向并列，逐条孤立地标更难保持一致。代价是跨 idea 漂移，靠下面的复核兜底
- **标完 12 个 idea 后做一遍复核**：只看 `yes` 和 `unsure`，问「按现在的标准这条还成立吗」
- 中途休息后，先重标 10 条已经标过的，对一下自己的一致性——人对不上自己，两人一致度就没意义

### Step 3 第二标注者

见第 8 节。只发那一段。

### Step 4 定稿

把两人的 `labels-*.json` 放进同一个目录，跑 `node .scratch/merge-labels.mjs <目录>`。
它写回 `labels.yaml` 的 `entries` / `agreement` / `frozen.expected`，并打印每个 idea 的 yes 数与 κ。细节见第 5 节。

## 3. 判定标准（rubric）

### 3.1 唯一问题

> **「如果我要做这个产品，这个仓库值不值得我读 10 分钟？」**

只依据 name + description + topics。**不许点进 README。**

原因很直接：插件拿到的就是这三样。你多看一眼，测出来的缺口就全是假的——你会用上插件根本拿不到的信息去判它错。

### 3.2 三档定义

**`yes` —— 三条必须同时满足：**

1. 它解决的是**同一个用户问题**（不是同一个技术，不是同一个词）
2. 读完它的 README，我大概率能抄到**至少一个具体设计决定**（数据结构、交互、权限模型、同步策略、prompt 结构、取舍）
3. 它是可运行软件 / 可复用库 / 模板，**不是** awesome-list、论文合集、课程、教程

**`no` —— 命中任一即是：**

1. 只共享关键词，用户问题不同（做 CRM 的 vs 做客服工单的）
2. 是基础设施但不是这个产品形态（idea 是「笔记应用」，对象是存储引擎）
3. 是列表 / 资源汇总 / 教程 / 课程
4. 同词异义（「agent」= 销售代理 vs AI agent）
5. 归档超过 2 年（判 `no`，理由里注明「可读不可抄」）

**`unsure` —— 描述不足以判断，且我不愿为它多花 1 分钟。**

`unsure` 率压在 20% 以内。超了不是标注者的问题，是描述质量的问题——这本身是产品信号，报告里单独写一行。

### 3.3 六个边界示例

| idea | 候选 | 判定 | 理由 |
|---|---|---|---|
| 自托管书签 + AI 打标签 | karakeep（"Bookmark app with AI tagging"） | `yes` | 同问题、可抄（标签管线 + 权限模型） |
| 同上 | miniflux（RSS 阅读器） | `no` | 形态相邻，用户问题不同 |
| 同上 | 某 awesome-bookmarks 列表 | `no` | 列表，不可抄实现 |
| 带 AI 打标签的书签 | linkwarden（AI 是附加能力） | `yes` | 主体问题相同；理由写「AI 为附加，主体可抄」 |
| RAG 知识库问答 | dify（LLM 应用平台，RAG 是模块之一） | `yes` | 可抄的是平台化设计，不是最小实现；理由要写清 |
| RAG 知识库问答 | llama_index（框架） | `unsure` | 框架还是产品？描述不足以判 |

> **唯一真正重要的一句：`yes` 的门槛是「能抄到具体决定」，不是「相关」。** 宁可 `no`，不要模糊 `yes`。

### 3.4 干扰项

每个 idea 塞 2 个「同关键词不同域」的仓库，`labels.yaml` 的 `interference_design` 已经写好了形态。用途是抓「只会说 yes」的标注者。

若干扰项被判 `yes`，说明「问题相同」和「关键词相同」没分清——回去重读 3.2 第 1 条，整批重标。

### 3.5 禁止事项（贴在标注者面前）

1. 不许点 README、不许看 star 数、不许看插件输出
2. 不许看完 README 回头改 label
3. 不许用「感觉有用」代替「能抄到什么」——`yes` 必须能一句话说出抄什么
4. 不许把 `unsure` 当 `no` 逃跑（也不许反过来）
5. 每条**必须**写理由，≤15 字，不写视为无效标注

## 4. 一致性

第二标注者独立跑同一批 240 条，只给第 8 节那段话，**不给你的答案、不给插件、不给 star**。

- Cohen's κ **≥ 0.6** → 可用，记进 `agreement`
- **< 0.6** → 不阻断定稿，但必须写清分歧集中在哪几类形态。**不要靠讨论凑一致**——凑出来的一致没有信息量，只是把两个人的偏差平均了一下

gold set 只取**权威标注者（人）**的 `yes`。另一位标注者的 yes 不进 `expected`，只用来标 `disputed`——并集会把两套「好结果」的定义混进同一个金集，之后无法归因。

**本次实测（2026-10-19，A vs 盲 AI 复核）：κ = 0.338，一致 149/240，分歧 91 条。** 剔除 unsure 后 κ = 0.416，说明主因不是「拿不准」，是判据不同。分歧集中在三类形态，记录为已知局限：

1. **生态 / 清单类仓库**（B3 11:0、E2 8:0）——`awesome-*`、SDK、参考实现算不算「可借鉴的答案」。A 收，AI 全拒。
2. **同平台相邻功能**（D1 7:0）——Obsidian「周计划 / 周回顾」插件 vs「把日记汇总成周报」。A 认为数据模型能抄，AI 认为问题不同。
3. **知名成品反向**（E1 1:3、B1 1:4、C2 6:0）——A 拒 `open-webui` / `joplin` / `twenty`，理由是「我已经知道的大牌，插件再推给我等于没干活」；AI 按形态相似收了。

三类指向同一条没写下来的判据：A 用的是「**对下一步有没有增量**」，AI 用的是「**形态相似**」。这一版金集采用前者（插件承诺的是「帮你找到想不到的项目」），但这条判据没进 rubric，换人重标复现不出来——**下次重标前先把它写进去**。

分歧条目标了 `disputed: true`，敏感性检查时跑一遍剔除版，别悄悄合并。

## 5. 定稿与导出

1. `merge-labels.mjs` 只把**权威标注者**（人，`--authority A`）的 `yes` 汇总成 `frozen.expected`；盲 AI 复核的 yes **不进** gold set，只用来把分歧条目标成 `disputed`
2. 凑不满 3 个 → 进 `frozen.sparse_ideas`，该 idea 只报「进池率」，不报绝对命中数（否则分母造假）
3. 人工确认 `frozen.expected` 后，把 `frozen.at` 记上日期、`meta.status: frozen`
4. 之后任何对 idea 文本的修改都要 bump `schema_version` 并全量重标
5. `agreement.kappa < 0.6` 不阻断定稿，但报告里必须写清分歧集中在哪几类形态、为什么没改 rubric

## 6. 字段说明

| 字段 | 谁填 | 说明 |
|---|---|---|
| `label` | 人 | `yes` / `no` / `unsure`，见第 3 节 |
| `reason` | 人 | **必填**，≤15 字。是后续判断 rubric 是否漂移的唯一依据 |
| `would_borrow` | 人 | 仅 `yes` 填，一句话。直接喂 E3 的 groundedness 检查 |
| `disputed` | 裁定 | 两人分歧未决 |
| `description` | 脚本 | 池子快照，原样复制，用于事后核对标注者当时看到的是什么 |
| `reason_is_default` | 脚本 | 理由仍是自动填的默认值、没改成更准的。分析理由分布时剔除这部分 |
| `reachable` | 脚本 | idea 的关键词是否出现在该仓库的**默认检索面**（名称/描述/topics）。`false` → 从失败分母剔除，单列「天花板」 |
| `reachable_evidence` | 脚本 | `name` / `desc-or-topics` / `search-channel`（我那条不带 `in:readme` 的搜索确实能搜到它）/ null |
| `reachable_keyword` | 脚本 | 命中的那个关键词，为空表示靠 `search-channel` 兜底 |
| `star_band` | 脚本 | `<200` / `200-1k` / `1k-10k` / `10k+`，分档而非精确值，避免分析时又被 star 带偏 |
| `archived` | 脚本 | 影响「可读不可抄」的解释 |

脚本补列在标注全部完成后统一跑一次，人不要一边标一边填——那等于提前给答案。

## 9. 常见错误

| 错误 | 后果 | 防法 |
|---|---|---|
| 先跑插件再建池 | 整个 idea 作废，不可逆 | 建池阶段不碰插件 |
| 标注时看 star | 长尾结论全废（star 偏差正是要测的东西） | `pools` 里根本不存 star |
| 看完 README 再判 | 测出来的是「README 检索面」，不是插件的 | 只给 name + description + topics |
| `yes` 给成「相关」 | 判分虚高，召回缺口被掩盖 | `would_borrow` 必填，写不出就不算 yes |
| 分歧靠讨论合并 | 一致度虚高，指标失去可信度 | 记 `disputed`，跑敏感性检查 |
| 中途往池里加好仓库 | 前后不可比 | 记 `notes`，等这一轮标完再决定是否重标 |

## 10. 与其他实验的关系

| 实验 | 怎么用这份金集 |
|---|---|
| E1 检索评测 | 直接跑：每个 idea 走一遍 `scout_projects` + `rank_candidates`，算 `Recall@pool` / `Recall@board` |
| E2 组件消融 | 复用同一批 idea，只换配置（关翻译 / relevance 固定 5 / 关长尾通道 / 无 inspect），比同一组指标 |
| E3 端到端任务 | 取 `expected` + `would_borrow` 作为 groundedness 的对照答案 |
| E4 故障一致性 | 不用金集，用故障注入矩阵 |
